# Intercept

Intercept is a loopback reverse proxy that loads websites through Rust, routes HTTP/HTTPS resources and application requests through a per-session origin, caches static assets, and presents a separately-originated authority panel. Rust owns the timer and enforces the selected request authorization policy.

## Status

This is a localhost reverse-proxy workflow, not a CONNECT/MITM proxy. A session opens at http://<session-id>.localhost:5000/p/<session-id>/.... Each session has a distinct browser origin, and its dashboard/authority controls are available at http://127.0.0.1:5000 or http://localhost:5000. The submitted website is the primary upstream origin; linked public HTTP/HTTPS origins are routed through origin-qualified paths beneath the same session origin.

## Run

Install a recent stable Rust toolchain, then run:

    cargo fmt
    cargo test
    cargo run

Open http://127.0.0.1:5000 or http://localhost:5000, enter the complete upstream URL (including any path and query string), and choose **Open new session tab**. Each launch creates an independent server-side session and opens it in a separate browser tab; the launcher remains open so you can start more sessions without restarting Intercept. The **Active Sessions** list shows sessions currently held by the process, lets you reopen one in another tab, provides a per-session folder button to browse cached resources, and provides a **KILL** action. The cache browser displays an origin/path folder tree, cached file metadata, text previews, and downloads. The cache is held in process memory rather than a disk directory; it disappears when its session is killed/expired or Intercept restarts. Killing a session removes it from the registry, cancels in-flight upstream requests, and clears its clients and cache without stopping the proxy process. The session opens the exact resource rather than resetting to the site's homepage. The session URL retains the destination path, query, and browser-side fragment. The browser sees a unique `.localhost` host for each session; the trusted authority panel is loaded in a cross-origin iframe. Allow pop-ups for the dashboard origin you use so each launch can open its own tab. Select an authorization policy before opening:

1. **Standard** holds POST, PUT, PATCH, and DELETE while allowing GET, HEAD, and OPTIONS, with narrowly-scoped read-only POST exceptions for YouTube autocomplete (`/youtubei/v1/complete`) and search (`/youtubei/v1/search`). Other POST endpoints remain held.
2. **Strict** permits the initial document bootstrap, then holds all upstream requests until the timer starts and expires.
3. **Custom** evaluates ordered host/path/method rules; unmatched requests use Standard behavior. Example:
   ```json
   [{"host":"example.com","path_prefix":"/api/","methods":["GET"],"hold":true}]
   ```
4. In the authority panel, enter a delay in seconds (0.000000001 to 86400; fractional values are supported) and press **[START]**. Rust owns the deadline and remains authoritative. Repeating the same Start request is idempotent; a different delay is rejected.

The server listens on the IPv4 and IPv6 loopback interfaces where available, and accepts the dashboard hostnames `127.0.0.1:5000` and `localhost:5000`. It is not intended to be exposed on a LAN or the public internet.

## Request path

    Browser
      |  HTTP to 127.0.0.1:5000 or localhost:5000
      v
    Axum loopback server
      - dashboard + session/timer API
      - multi-origin URL routing and response rewriting
      - bounded per-session static-resource cache
      - minimal bottom authority banner
      - per-session authorization gate
              |  HTTP or verified HTTPS (rustls)
              v
          Upstream origin

One reqwest Client is created per upstream origin and reused. Each new origin is DNS-resolved, non-public answers are rejected, and the client is pinned to the resolved addresses to reduce DNS-rebinding/SSRF risk. TLS certificate verification remains enabled. Regular document and transformable resource requests have a 120-second total upstream deadline; AJAX streams retain their separate 24-hour deadline. Opaque/non-cacheable responses and known resources larger than the cache-entry limit are streamed. Rewritable HTML/CSS/JavaScript and small cacheable assets remain buffered, with a 32 MiB response ceiling. CSS, JavaScript, images, fonts, and WebAssembly responses are cached in a bounded 64 MiB per-session cache (up to 8 MiB per entry, five-minute default TTL); HTML and API responses are not cached by default.

## Authority behavior

- The proxied page keeps its original layout. A fixed cross-origin authority iframe appears at the bottom with WAITING / AUTHORIZATION COUNTDOWN / AUTHORIZED, a decimal-seconds delay input, **[START]**, the countdown, and a notice. **[EXPAND]** grows the bottom panel to 50% of the viewport so the live event stream and metrics can use the available space; **[COLLAPSE]** restores the compact 148px bar.
- The iframe is hosted on the dashboard origin, isolated from the proxied page by the browser's same-origin policy and a closed Shadow DOM host. The session origin cannot access the dashboard control API; API requests are accepted only on either trusted dashboard hostname, with Origin required to match the corresponding hostname.
- Authority status, event polling, and event uploads have full-response deadlines and in-flight guards. The countdown advances locally between server status responses; Rust's monotonic timer remains authoritative. Start retries using the same delay are idempotent.
- The controller observes pointer, click, change, input, and keydown activity; reports selected event-listener registrations; and records fetch, XHR, sendBeacon, and proxied HTTP request metadata. Recent input/change/Enter events receive short-lived IDs attached to subsequent fetch/XHR requests, allowing the event stream to correlate a typed interaction with its AJAX request and upstream response. It records target selectors and event IDs only, never input values or request bodies. URL-like event targets are stored without query strings or fragments so signed media URLs and embedded session URLs are not retained in diagnostics.
- When a SABR response contains stream-protection status `3`, the proxy emits `youtube_sabr_attestation_context` with the session's cumulative WAA RPC count and last operation/ID/age, plus separate `/youtubei/v1/att/get` and `/youtubei/v1/att/log` request counts and last IDs/ages. These resource counts are separate from WAA `Create`/`GenerateIT` RPCs. Match each `rpc=` ID with browser dispatch/response, proxy receipt/ingress, and upstream-response events. Every GenerateIT request received by the proxy emits `youtube_attestation_freshness phase=generateit_request_context` with its playback-context ID and `status3_relation=after|before|none`: `none` means no status-3 record exists in that context, while `before` means the request began before the recorded status 3. A `phase=generateit_after_status3_request` event means the GenerateIT request itself reached the proxy after the latest observed status-3 response; the matching `phase=generateit_after_status3` event means that same request later received upstream HTTP 200. Requests that began before status 3 are not counted as refreshes merely because their responses completed afterward. These events establish transport ordering, not whether Google accepted an attestation. This distinguishes a missing challenge request, a logging-only request, and a WAA RPC that actually reached the proxy.
- YouTube attestation-resource discovery also recognizes scripts under YouTube's `/s/player/` runtime path, even when filenames do not mention BotGuard or attestation. Dedicated/shared worker construction, worker errors, message types, unhandled runtime rejections, and service-worker initial/controller/message lifecycle are observed without reading application message payloads, blob identifiers, or URL queries. Dedicated YouTube workers receive a one-time private playback-context handoff consumed by the injected worker bootstrap; subsequent WAA fetch/XHR requests carry the page's playback-context correlation header. Shared workers and service workers remain unscoped because they may be shared across multiple pages. JavaScript Blobs created on YouTube pages receive a guarded worker-only bootstrap so Blob-backed workers route fetch, XHR, and `importScripts` through the session, just like network-loaded workers. The bootstrap exits in window contexts, and it forwards the worker's native requests rather than generating or modifying attestation data.
- For first-party YouTube `/api/stats/qoe`, `/api/stats/watchtime`, and `/api/stats/playback` requests, the proxy rewrites a session-local `euri` query parameter back to the real upstream page URL, matching the existing Origin/Referer virtualization. It records only whether `euri` was present and whether it was rewritten; the parameter value is never logged.
- YouTube playback diagnostics attach metadata-only listeners to dynamically inserted `<video>` elements and report playback lifecycle events (`playing`, `waiting`, `stalled`, `error`, `timeupdate`, buffering, and seek transitions). Events include rounded playback time, duration, ready/network state, buffered-range summaries, buffered-ahead seconds, video dimensions, media error code, browser-exposed total/dropped/corrupted frame counters, element connectivity, and source-presence booleans; time/progress samples are throttled. An independent one-second playback watchdog records an initial `clock_stalled` event after 4.5 seconds without media-time advancement, 12-second active-playback heartbeats, and `clock_resumed` when the playhead advances again. It separately detects active playback requests that remain below HAVE_CURRENT_DATA (`ready_state<2`) for 4.5 seconds, even if the rounded playhead appears to move: these produce `playback_unready`, 12-second `playback_unready_heartbeat` events, and `playback_ready` on recovery. Readiness events include the current media snapshot and a coarse cause such as hidden tab, no source, unselected source, no current frame data, or no buffer ahead. Watchdog events include time since last advancement, buffer-ahead, ready/network state, frame counters, source-presence booleans, visibility state, and a coarse stall classification. Source URLs and media payloads are never recorded. These metrics help distinguish media delivered by SABR from media appended to the player buffer and frames subsequently decoded or dropped, and distinguish a newly inserted/unconfigured video element from a selected source. The proxy also reports UMP framing bytes separately from payload bytes so the parsed stream byte total can be compared with the upstream response byte count. The proxy also records elapsed time between SABR request arrivals and between the previous completed media response and the next request, which helps distinguish player scheduling gaps from upstream request/stream failures.
Player teardown instrumentation also emits `youtube_player_media_mutation` for video `src` / `srcObject` changes, `<source>` attribute and child-list changes, video detachment, and `HTMLMediaElement.load()` calls. These events record before/after presence flags and sanitized caller frames only; they never include media URLs or source values. The page sends its existing playback-context ID with telemetry uploads, allowing player-state, watchdog, and media-mutation events to be annotated with the matching status-3 request ID and the event's wall-clock elapsed time relative to that status-3 observation. This is diagnostic only and does not change native media operations or retry behavior. Media-mutation events retain up to six sanitized caller frames (rather than two) so teardown traces can expose the function that invoked `stopVideo()` or the operation that cleared a media source; timer diagnostics retain their existing two-frame limit. YouTube's player `base.js` also receives narrowly-scoped, metadata-only instrumentation for the SABR protection-token recovery path. `youtube_sabr_recovery` events report the `spsumpreject` state, whether content/session token recovery was requested, provider readiness, token-result presence (never token values), token-release checks, calls that clear the loader gate, and whether the expected source hooks were installed. These events are correlated to the latest status-3 RID using the page playback-context header. Additional lifecycle probes mark entry into the token-controller initializer (`F0a`), starter (`iT`), and disposer (`Upb.ka`), including only boolean snapshots of the owning controller's active, pending, and release state. The base instrumentation status reports whether each lifecycle hook matched the current minified bundle. A separate `youtube_player_error` event marks entry into every matched YouTube `handleError` definition (up to 16 per bundle) and records only argument types, bounded numeric scalars and own numeric error-code fields, coarse video state, and up to four sanitized caller frames; string argument contents and stack URLs/queries are never retained. The base instrumentation status reports both whether a handler hook matched and the number of definitions instrumented. Instrumentation is applied only to YouTube `base.js` bundles and does not modify token generation, controller assignments, request scheduling, protection statuses, or playback behavior.

- YouTube Web Attestation API diagnostics correlate each observed page/worker RPC with proxy receipt and upstream response using a per-request opaque ID carried in an internal `X-Intercept-Attestation-Id` header. The proxy validates and strips this header before upstream forwarding; the value is metadata only and is not part of YouTube's request. They also retain an `Other` candidate for related Google API paths containing `Waa`. The `youtube_attestation_resource` event recognizes the InnerTube `/youtubei/v1/att/get` challenge and `/youtubei/v1/att/log` logging requests, including proxy receipt/ingress and upstream response/error metadata. Primary-origin `/p/<session>/...` URLs are unwrapped before host/path classification, so proxied YouTube player bundles and same-origin attestation requests are attributed to their upstream host rather than localhost. The `youtube_attestation_rpc` event records page/worker dispatch, Resource Timing, early Rust proxy receipt (`proxy_received`), completed request-body buffering (`proxy_ingress`), upstream response-header/error phases, and browser response completion; challenge retrieval is reported as `youtube_attestation_resource`. Page-window `youtube_attestation_rpc phase=dispatch` records also include a sanitized caller stack (up to four frames, with function name, host, script basename, and line/column) plus the age and metadata-only snapshot of the latest observed video-element state at RPC creation. This helps identify whether a GenerateIT request originated in a player callback and what the media element was doing immediately beforehand. Stack URL queries, request/response bodies, challenge data, attestation values, cookies, source URLs, and account/session identifiers are not recorded; worker-originated calls do not have a window video-state snapshot. For GenerateIT specifically, the page controller also observes `setTimeout` and `setInterval` callbacks registered from YouTube's `kevlar_base_module`/`kevlar_main_mod` and `m=base` bundles. Registration records identify the runtime (`kevlar` or `base`) and are deduplicated with a 96-site per-page cap. It emits one deduplicated `youtube_player_runtime phase=timer_registered` record per unique timer registration site (up to 32 per page), including timer type, requested delay, callback name, and sanitized scheduling callsite. It also retains a bounded, 15-second in-memory window of recent timer fires and attaches timer summaries to the next GenerateIT dispatch. Timers with delays of 100 ms or less are shown separately as `pollers`. Slower timers retain their latest fire timestamp in a separate bounded registry (64 timers, 15-second recency window), so bursts of zero-delay callbacks cannot evict the slower-job context. Each summary labels its relation to dispatch as `active` only when the GenerateIT dispatch occurs synchronously inside that timer callback; otherwise it is `recent`. This separates direct callback correlation from mere temporal proximity while keeping high-frequency polling visible. This is observational only: timer delays and callback order are not changed, and no GenerateIT call is initiated by the instrumentation. The separate `youtube_attestation_resource` event records likely BotGuard/WAA script load/error/runtime-error/CSP-block and worker construction/error events using host+path only. XHR outcomes distinguish response headers, completed response, network error, abort, timeout, and an unexpected `loadend` without a preceding terminal event. Google-hosted JavaScript resources are also listed as candidates by host+path so the actual loader URL can be identified even when its filename does not contain a BotGuard/WAA marker. These diagnostics never inspect WAA request or response payload bodies and never log URL queries, challenge data, token values, cookies, or account/session identifiers. The separate SABR framing scanner reads only the protobuf structure needed to report `po`/`pc` presence and byte lengths; it skips opaque token and cookie values without copying or retaining them. Resource Timing may expose only timing/size metadata for cross-origin requests. A script load is evidence of successful resource loading, not proof that its code executed successfully; an HTTP success records transport success only, not integrity-token generation or acceptance. Requests that bypass both page/worker observers and the session proxy remain invisible. The proxy observes and transparently forwards the site's native WAA flow; it does not synthesize or replay attestation tokens. For each later SABR request, `youtube_sabr_request_metadata` snapshots the latest WAA upstream response operation, opaque RPC ID, HTTP status, content type/length/encoding, and response age alongside the request's parsed `po` token-presence and byte-length metadata. These diagnostics report only presence/length, never proof or token contents.
- The browser briefly defers anchor navigation and form submission only while cookie-bridge writes are pending, using a bounded queue (50 actions) so a new document cannot overtake a cookie update. Authorization is enforced by the Rust request gate for every routed upstream request: Standard, Strict, and Custom policies therefore apply consistently to AJAX, forms, links, and document navigations.
- HTML resource rewriting applies to generic `href`/`src` and related resource attributes, including SVG `<use>`/`<image>` references and custom elements, so cross-origin icons are routed through the session before the browser loads them. Network URLs created at runtime through fetch, XHR, sendBeacon, EventSource, Worker, SharedWorker, service-worker registration, window.open, dynamic URL attributes, and CSS setters are routed through the session. Pages enforcing Trusted Types receive a narrowly scoped `intercept-proxy` TrustedScriptURL policy for same-session script URLs; the controller records individual rewrite failures without aborting its remaining initialization. Worker scripts get a bootstrap that routes worker fetch/XHR/importScripts calls and marks fetch/XHR as AJAX. Static and dynamic JavaScript module imports are rewritten too.
- **AJAX passthrough:** requests explicitly marked by the injected fetch/XHR controller (with browser Fetch Metadata and EventSource fallbacks) (\`Sec-Fetch-Dest: empty\`), legacy \`X-Requested-With: XMLHttpRequest\`, an explicit internal AJAX marker, or \`Accept: text/event-stream\` use a dedicated response path. The upstream status, content type, application headers and response bytes are preserved; HTML/CSS/JavaScript rewriting and the static-resource cache are bypassed. Upstream response bodies stream back to the browser instead of being buffered.
- `Location` headers are rewritten to the session URL space. Upstream `Set-Cookie` headers are consumed by the session-owned cookie jar instead of being exposed to the browser’s synthetic `.localhost` cookie store. The jar applies upstream domain and path matching when sending cookies back to each origin. `Origin` and `Referer` are translated back to the upstream site before forwarding; Intercept control headers are never sent upstream.
- AJAX response streams have a 24-hour total request timeout so long-polling and Server-Sent Events can remain open; browser EventSource clients can reconnect after that limit. Request bodies are still buffered and capped at 8 MiB. The AJAX response path has no 32 MiB body-buffering cap.
- Each session has one in-memory cookie jar shared by its pooled, DNS-pinned upstream clients. JavaScript `document.cookie` reads and writes are bridged against the document capability's upstream origin (including after canonical-host redirects), with `HttpOnly` cookies hidden from page JavaScript and bridge capabilities bound to that document’s upstream origin. Explicit secondary-origin proxy paths must match the same capability. Cookie state is removed when the session ends or Intercept restarts. `localStorage` and `sessionStorage` keys are namespaced by upstream origin within the session, including filtering of cross-origin storage events. A session may initialize at most 24 upstream-origin clients.
- Static non-AJAX resources are cached per session in memory (64 MiB total; 8 MiB per entry; five-minute default TTL). HTML and API responses are not cached by default. Use the folder button beside **KILL** in the dashboard to browse the live cache by scheme, host, and path, preview text assets, or download cached bytes. This is a virtual browser over RAM entries, not a disk-backed file manager.
- Rust owns authorization. Standard blocks POST/PUT/PATCH/DELETE except the explicit read-only YouTube autocomplete/search routes; Strict holds all proxied traffic after the first bootstrap document; Custom applies ordered path/host/method rules and falls back to Standard. A site's state-changing GET endpoints remain allowed by Standard and must be covered by Custom or Strict.

This is not a universal JavaScript sandbox and cannot suspend arbitrary JavaScript execution. The event stream is observational; it records event metadata, not values. The browser queue defers ordinary anchor navigation and form submission, while the Rust proxy is authoritative for POST, PUT, PATCH, and DELETE. A page's custom click handler may still perform local JavaScript side effects before making a request, and applications can mutate state through GET endpoints. Those behaviors are not universally blocked.

## Rewrite directory

The rewrites/ directory contains the authority-banner stylesheet and the extension point for future site-specific rewrite rules. The HTML/CSS/JavaScript transformers change network URLs only to route resources through the active session, then append the banner. The injected JavaScript controller routes runtime-generated HTTP requests, observes page-action metadata, and defers link/form navigation until timer authorization. Rust classifies AJAX requests independently and streams their upstream responses without document/resource transformations.

## Boundaries and limitations

- **Not transparent HTTPS interception:** the browser uses local HTTP and sees the local proxy URL. Rust independently establishes upstream HTTPS with normal certificate verification. This workflow does not need a browser-installed CA because the browser connection to Intercept is HTTP. It does not preserve the original https://host/ address bar.
- Preserving original HTTPS hostnames while inspecting their traffic requires configuring the browser/network to send traffic through a CONNECT proxy and trusting a local interception CA in that browser. This code does not implement that MITM mode.
- HTTP and HTTPS resources for public origins are routed through the session. Worker and service-worker registration/network hooks are partially supported, but service-worker lifecycle/origin semantics still vary by browser and site. WebSockets, WebTransport, HTTP/3, native navigation APIs that bypass the patched URL surfaces, and transparent TLS interception are not implemented.
- The browser origin is localhost, not the original upstream origin. Origin-sensitive applications may still behave differently even though request URLs, Origin, Referer, and cookies are translated where possible. This is a reverse proxy, not a browser-origin emulator.
- The in-memory asset cache is per process and per session; restarting Intercept clears it. Dynamic HTML and API responses are deliberately not cached.
- CSP source directives are adapted to allow the localhost-routed resources. This changes the effective security policy of the proxied page; only browse sites you trust.
- Proxied page scripts execute in their own per-session origin, separate from the dashboard and authority API. The Host/Origin guard rejects session-origin access to dashboard control endpoints. This reduces cross-session and dashboard exposure, but is not a complete browser sandbox or an audited security boundary; only open websites you trust.
- The IP checks and per-session DNS pinning reduce common SSRF/DNS-rebinding paths, but this is an early-stage development tool, not an audited security product.

## Configuration

The server remains loopback-only and accepts both `127.0.0.1:5000` and `localhost:5000`. Restarting the process clears sessions and timers. Logs use the RUST_LOG environment variable (default: intercept=info) and include per-request correlation IDs.

Resource-limit environment variables:

| Variable | Default | Meaning |
|---|---:|---|
| `INTERCEPT_MAX_SESSIONS` | 8 | Maximum active sessions (1–256) |
| `INTERCEPT_SESSION_IDLE_SECONDS` | 1800 | Idle-session expiration (60–86400 seconds) |
| `INTERCEPT_MAX_INFLIGHT_PER_SESSION` | 64 | Concurrent upstream requests per session (1–512) |
| `INTERCEPT_REWRITE_WORKERS` | CPU count | Maximum concurrent blocking rewrite workers |
| `INTERCEPT_AUTH_POLICY` | standard | Default policy when the launcher omits one |

The dashboard reports the active-session count against `INTERCEPT_MAX_SESSIONS` and lists each active session with its target URL, policy, and authorization state. The list is refreshed after each launch or on demand. The authority UI for each tab reports cache bytes, initialized upstream origins, in-flight request counts, selected policy, and last activity. Sessions are pruned every minute; sessions with active requests are retained.

## Firefox native-origin mode (YouTube)

Intercept also includes an optional Firefox extension mode for YouTube. Unlike the reverse-proxy mode, it leaves the browser connected directly to YouTube: the page, dedicated workers, service workers, cookies, media requests, and TLS connection retain their native browser context. The extension observes selected YouTube and Google request lifecycle metadata and forwards sanitized events to the local Rust event store.

**Important:** this initial native-origin mode is observation-only. It does not route request or response bytes through Rust, enforce Standard/Strict/Custom authorization rules, hold and replay requests, rewrite payloads, or populate the reverse-proxy cache. Those controls remain available in reverse-proxy mode. No request headers, cookies, tokens, bodies, response bodies, or URL query strings are captured by the extension.

See extension/firefox/README.md for installation and use.
